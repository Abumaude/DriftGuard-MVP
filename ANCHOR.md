# DriftGuard — Design Anchor Document

## Single source of truth for the DriftGuard public launch

**Version:** 1.0
**Date:** 2026-07-31
**Build method:** Agentic engineering, governed by this anchor

> **This is the self-evidencing artefact.** DriftGuard claims that a project governed by an anchor survives sessions, tools, and operators. The cheapest way to test that claim is to govern DriftGuard's own launch with it and publish the result. This file is that anchor. Its gate is currently **closed** — see Section 1.0 — and it is published closed on purpose, because a governance methodology that quietly waives its own front gate has already lost the argument.

---

## 0. How to use this document

This is the **immutable design anchor** for the launch. AI agents read from it and never modify it. If an agent's output contradicts this document, the output is wrong.

Section 1 is loaded into every session as mandatory context. All other sections are loaded selectively — only when `BUILD_INSTRUCTIONS.md` routes to them. Every section is self-contained: an agent reading Section 5 should not need Section 6 to understand it. The validation checklist in Appendix A runs after every build step.

The anchor grows by **section addition**. Sections are not edited and not versioned in place. If a decision changes, a new section records the change and why, and the old one stays as the record of what was believed at the time. That is the difference between a constitution and a wiki page.

## 1. Architecture anchors (immutable context)

### 1.0 Ship-or-drift front gate

> This exists so that **[NAMED PERSON — OPERATOR MUST FILL]** can **stop re-explaining their project to their AI every time they open a new session, and hand it to someone else without a three-day briefing**, and I will know it worked when **they fill in an anchor for a project of their own and come back with a specific complaint about it**.

**GATE STATUS: CLOSED.** The first slot is empty. Under this methodology's own constraint 1, no build action past Step 0 is permitted until it holds the name of a real human who can be messaged today.

This is not an oversight and it is not to be filled with "alpha users," "vibe coders," or "solo founders." A demographic cannot reject you; a person can, and that discomfort is the entire mechanism. The gate stays visibly closed in the published repository until a real name is written in, and the fact that it is closed is itself the demonstration.

**Slot tests, each of which must pass before building:**

The **named person** is a human with a name, reachable this afternoon. The **result** is a change in *their* world, not a feature of the tool — "governance methodology for AI-assisted work" is a feature; "stops re-explaining and can hand it over" is a result. The **signal** is generated by someone other than the operator; "I published the repo" is not a signal, "they filled in an anchor" is.

#### Ship cadence

> Chosen cadence: **every step**

Each build step ends with an exposure. This is the strictest setting and it is chosen deliberately, because the specific failure this project exists to correct — twenty variants built, none shipped — is precisely the failure a loose cadence permits. Overrides are never blocked, only logged, one line each in `state/use-ledger.md`. A run of overrides is itself the signal that the architect's trap has reopened.

#### Signal and feedback ladder

| Release band | Named-person reach | Feedback request | Signal that counts |
|---|---|---|---|
| **Prototype** | One named person | Send the repo link and ask one question: *"Could you fill in an anchor for something you are building?"* | They reacted, or told you why not |
| **MVP** | 5–15 named people in the role | Watch them attempt to fill an anchor, unaided, and ask the one blocker question at the point they stall | They filled it in and came back with a specific complaint |
| **v1** | Public | Publish the wedge; ask what they would pay for and what they would not | They used it on a second project, or they paid |

Note what the MVP signal is not. It is not stars, forks, or traffic. Those are quarantined metrics — real, worth watching, and unable to tell you whether the methodology works. A specific complaint from someone who filled in an anchor is worth more than a thousand stars, because only one of the two proves the artefact was used.

### 1.1 Product definition

DriftGuard is a governance methodology for AI-assisted work — a small set of plain-markdown files and a protocol that keep a project's decisions and memory portable across sessions, tools, operators, and domains, for builders whose projects outlive a single chat. Success is that a person other than the operator fills in an anchor for their own project, uses it across at least two sessions, and returns with a specific complaint about it.

### 1.2 Immutable constraints

Constraints 1–6 are inherited from the Ship-or-Drift methodology and apply to every project. They are not edited or removed. Project-specific constraints start at row 7.

| # | Constraint | Overridable | Implication |
|---|---|---|---|
| 1 | No build action until the anchor sentence (1.0) holds a real name | No | The launch cannot proceed past Step 0 while the gate is closed |
| 2 | Every new feature must be justified by a signal you *observed*, not one you imagined | No | "Users would probably want" is not a justification |
| 3 | An exposure to the named person happens at the cadence set in 1.0 | Yes — logged | Skipping requires a one-line drift-log override with a reason |
| 4 | "Done" equals the named person's behaviour, never your sense of completion | No | A step is not done because the file is written |
| 5 | No exposure ships without its band's feedback request attached | No | Shipping without a request produces output, not outcome |
| 6 | A release band is entered only after the previous band's signal is observed | No | The hard floor. No cadence setting and no override crosses a band boundary |
| 7 | DriftGuard makes zero API calls and requires no server, account, or telemetry | No | Anything requiring a backend belongs in a separate product, not here |
| 8 | No new variant is designed while an unshipped variant exists | No | The architect's-trap protection. This is the constraint most likely to be violated |
| 9 | Every public claim about a competitor, a paper, or a vendor carries a verifiable source and a verification date | No | Stale competitive claims are the exact failure being sold against |
| 10 | The anchor grows by section addition; no section is edited or deleted | No | Superseded decisions stay visible as the record of what was believed |
| 11 | Any figure quoted publicly comes from the primary source, never a summary of it | No | The "10%" incident in the research log is the standing example |

Constraint 8 has teeth this quarter specifically. The research log's July scan identified positioning work, a rename, and an unattended-build provision — all of which are tempting as new factory chats and none of which are permitted to precede the launch shipping.

### 1.3 Design principles

| # | Principle | Test question |
|---|---|---|
| 1 | Ship-or-drift front gate | Does this session end with one exposure, carrying its band's feedback request, in front of the named person? |
| 2 | One screen at first contact | Can someone landing on this repo understand what it is and start, without scrolling past one screen of orientation? |
| 3 | Concede before distinguishing | Does this copy acknowledge what a competitor genuinely does better before claiming any difference? |
| 4 | Every claim sourced and dated | Can a hostile reader verify this sentence in under a minute? |
| 5 | Rename-cheap | Does this artefact depend on the string "DriftGuard" in a way a find-and-replace cannot fix? |
| 6 | No API calls | Does this require a key, a server, a quota, or an account? If yes, it is out of scope |

### 1.4 Foundational context

DriftGuard emerged from a diagnosed failure — the architect's trap, in which producing architecture substitutes for shipping product. Roughly twenty variants, six memos, two design systems, and an ID schema existed before anything was published. The methodology is the correction, and the launch is the first test of whether the correction holds.

The competitive position changed materially in mid-2026. GitHub Spec Kit popularised the per-project constitution at very large scale, and vendor platforms began absorbing cross-session memory. Neither closes the seam this project addresses — continuity *between* repos, sessions, operators, and non-code domains — but both mean the launch must lead by conceding rather than by differentiating. The full analysis is in `docs/POSITIONING.md`; the evidence is in `docs/RESEARCH_LOG.md`.

The first market is the non-technical AI builder: someone who has watched a project tangle and had no way to untangle it. This is also the current weak point, because the artefacts are written in developer register. That gap is named openly rather than hidden.

## 2. Substrate

Git-native markdown with YAML frontmatter. The anchor is the constitution: it grows by section addition and is never edited or versioned in place. Plain text any model or human can read, neutral between agent, contractor, supervisor, and operator, and neutral between tools.

Three files carry the whole system. `ANCHOR.md` holds stable knowledge — what this is, who for, the rules. `BUILD_INSTRUCTIONS.md` holds status — the sequence, which step is next, what each step loads. Git holds memory — state in the repo, not in a chat or on a machine. `state/use-ledger.md` holds procedural memory: what was tried, what failed, what was skipped and why.

That three-way split is not an aesthetic choice. It matches, independently, the separation Meta's long-horizon-agent work arrived at for its memory bank (status, knowledge, procedural), which is the closest thing to external validation the substrate design has.

---

## 3. Protocol

The anchor schema (Section 1 mandatory, all else routed). Section routing in `BUILD_INSTRUCTIONS.md`, so each step loads only what it needs and context never overflows. Handoff blocks at session end. The use ledger. Compliance levels — Basic (anchor only), Standard (anchor plus build instructions), Full (adds ledger, dependency graph, and verification loop).

The rules of how the files are written, read, and obeyed. The protocol is the product; the files are its instance.

## 4. Launch surfaces (v1 scope — locked)

Five surfaces. No sixth is added without amending this anchor by adding a section.

The **master repository README** is the landing page for the whole methodology, and the marketing surface. There is no separate marketing website. The **public dashboard** (`docs/index.html`) is a GitHub Pages page rendered entirely from committed JSON in `docs/data/` — a launch surface and a live demo in one, shareable by URL. It calls no API: design principle 6 bars anything needing a key, server, or quota, and the unauthenticated GitHub API is quota-bound. The **build tracker** (`docs/tracker.html`) is the operator instrument, showing variant and feature state from `docs/data/tracker.json`. The **variant repository READMEs** follow one grammar across all of them. And the **long-form channel** carries the origin story and the positioning argument at length.

Explicitly out of scope for v1, recorded so it does not resurface by accident: a separate marketing website, per-variant dashboards, a custom design system pass (the selection chat is gated on exports that do not exist yet — placeholder tokens ship and are swapped later), wireframes for simple surfaces, and any backend.

## 5. Naming

The name is provisional and the `DriftGuard` GitHub organisation is taken. Publishing proceeds under an alternative organisation name with a visible provisional note on every public surface.

Three verified collisions are recorded with dates in `docs/NAMING.md`, along with selection criteria and a one-pass rename procedure. Every occurrence of the name in this repository is the literal string `DriftGuard` or the slug `driftguard`; both dashboards read the name from a single constant. Nothing depends on the string in a way a find-and-replace cannot fix — this is design principle 5, and it is what converts a naming problem from a crisis into a scheduled operation.

## 6. Release bands

### Prototype band — signal: a reaction from one named person

- [ ] Gate filled: a real name in Section 1.0
- [ ] Repository public under an available organisation name
- [ ] README, anchor, build instructions, templates, and one worked example live
- [ ] Both dashboards deployed and reachable by URL
- [ ] Scope Lock verification resolved (see `docs/RESEARCH_LOG.md` — currently unverified)
- [ ] Link sent to the named person with the Prototype feedback request attached

**Proof gate to exit:** the named person reacted, or explained why not.

### MVP band — signal: repeated, unaided use by a handful

- [ ] Feedback intake live: issue templates, discussions, a short form, a booking link
- [ ] 5–15 named people reached individually, not by broadcast
- [ ] At least three watched attempting to fill an anchor
- [ ] Non-technical register pass on the templates, driven by observed stalls
- [ ] Variant repositories published for every variant marked complete

**Proof gate to exit:** someone other than the operator filled in an anchor, used it across two sessions, and returned with a specific complaint.

### v1 band — signal: payment or public adoption

- [ ] Capture-plugin wedge MVP shipped
- [ ] Rename executed
- [ ] Public launch across the wider surfaces
- [ ] Pricing decision locked and recorded as a new anchor section

**Proof gate to exit:** used on a second project by someone else, or paid for.

### Out of scope permanently

A hosted service, an account system, telemetry, and anything requiring an API key to use the methodology itself. These would convert DriftGuard into a harness, which contradicts constraint 7 and destroys the only durable advantage it has.

## 7. The commercial trust layer ships with this repo (2026-07-31)

**This section is an addition, not an edit.** Nothing in Sections 0–6 is retracted.

### 7.1 What is included and on what terms

The Commercial Trust Layer v0.1 is published at `commercial/` — a twenty-rule commercial constitution, an evidence ledger, an honest-disclosure pattern, product and funnel profiles, a pre-ship checklist, a post-purchase outcome standard, and a measurement spec.

It ships **as a resource, held verbatim, for anyone using this repo to adopt in whole, in part, or not at all.** It is not ratified as binding law over this project and it imposes no new constraints on Sections 1–6. Section 1.2 is unchanged: constraints 1–11 remain the complete set.

The reason for that choice is the same reason the layer is worth including at all. A commercial standard adopted because it arrived in a folder is not a standard, it is a habit — and a project whose whole thesis is that decisions should be deliberate has no business quietly binding itself to twenty rules it has not argued with.

### 7.2 What was done with it before publishing

It was run once, against this repo's own README, on 2026-07-31. That run caught three defects in a file that had survived an adversarial review pass earlier the same day: a synthetic example presented as evidence, an unmeasured figure stated as a measurement, and internal review carrying an implication of independence.

All three were corrected, and the corrections stand on their own merits regardless of whether the layer is ever formally adopted. Labelling invented examples, withdrawing numbers nobody measured, and disclosing who did the verifying are not favours to a governance document — they are things that were simply wrong and are now right.

The run is recorded in `commercial/CHECKLIST_RUN_2026-07-31.md`, failures first.

### 7.3 Why the earlier review missed them

Worth keeping as a finding. The adversarial pass hunted internal contradictions and broken logic, and found thirty-six. These three are a different class — each internally consistent, each individually defensible, and collectively the difference between a document that informs and one that persuades slightly past its evidence. Adversarial review and commercial governance are not substitutes for one another.

### 7.4 If it is ever ratified

Ratification would be a new appended section, not an edit to this one, and it would say which of the twenty rules bind this project and which do not. Until such a section exists, the layer is a resource in a folder and nothing more.

## 8. The closed-loop gate (adopted 2026-08-22)

**Addition, not an edit.** Nothing in Sections 0–7 is retracted.

### 8.1 What the ruling requires

`RULING_closed-loop-gate-v1` was ratified on 2026-08-22 and applies to the master templates and every future variant; existing variants adopt on next touch. It requires three things.

Every anchor carries an **Actor Loop Closure table** in its core-loop section: for each actor who can trigger a state change, how they learn the outcome and where they go to check. A blank cell is a missing feature.

Every build file runs a **process walkthrough gate** before any code — draw the whole process, walk each actor's journey end to end, halt on any journey that ends without its actor learning the outcome. It carries an `operator_review` flag, `required` by default, so a human approves the drawing before building starts.

Every validation checklist gains a **NO DEAD ENDS** item, re-run after every step rather than only at the start.

Both templates in `templates/` now carry all three. The ruling itself is at `docs/RULING_closed-loop-gate-v1.md`.

### 8.2 Where it sits in the sequence

The ruling numbers the walkthrough as Step 0. Here, Step 0 is already the ship-or-drift front gate, so the walkthrough is **Step 0.5** — immediately after, and before any build work.

That ordering is the point rather than a workaround. Step 0 asks whether this should exist at all. Step 0.5 asks whether the design is complete. The interesting failure is a product that passes the first and fails the second: real person, real need, and a process that quietly leaves somebody hanging.

### 8.3 Why per-feature testing does not catch this

Worth stating in the anchor because it is the reasoning that makes the gate non-optional.

Testing proves each part works. It never proves the process closes. In the case that produced the ruling, submission worked and admin approval worked — both would pass every test written for them — and the submitter had no way to find out what had been decided. An omission contradicts nothing, so nothing fails. Only walking the whole journey surfaces it, and a drawing surfaces it in minutes rather than after hours of building.

### 8.4 Applied to this project, and what it found

Running the table against the launch itself:

| Actor | Action | State change | How they learn the outcome | Where they check |
|---|---|---|---|---|
| Operator | Completes a build step | `step-XX` commit, ledger line appended | Status report at the end of the step | `git log`, `state/use-ledger.md` |
| Named person | Receives an exposure with its question | Their reply becomes the band signal | Operator responds directly | The message thread they replied in |
| Adopter | Fills an anchor for their own project | Their repo gains a governance record | Their own AI answering from the record instead of inventing | Their own repo |
| Adopter | Attends a watch-me-try-it session | Their stall is logged | They see the log entry being written, live | The call itself |
| **Feedback filer** | **Opens an issue or a Discussion** | **Enters an untracked queue** | **Nothing stated** | **Nowhere** |
| **Contributor** | **Opens a pull request** | **Enters an untracked queue** | **Nothing stated** | **Nowhere** |

The last two rows are dead ends, found by running the gate on ourselves.

The README says support is "one person, with no response-time commitment", which is honest about *speed* and silent about *whether anything happens at all*. Somebody files the most valuable thing this project can receive — a specific complaint from a real user — and has no way to learn whether it was read, accepted, or ignored. Under the ruling that is a missing feature in the spec, not a nicety to add later.

**Fix, before the repo is public:** state plainly, in `CONTRIBUTING.md` and in the issue templates, what happens after somebody files — that every issue gets a reply or a close with a reason, that feedback which changes the product gets recorded in the use ledger with the issue number, and that the ledger is public so a filer can see their own report land. That closes both rows with existing machinery and no new tooling.

Recorded here rather than quietly fixed, because a gate that finds something on its first run is worth more evidence than a gate that finds nothing.

### 8.5 Scope

This section adopts the ruling for the templates, this anchor, and the worked example. It adds no constraint to Section 1.2 — the NO DEAD ENDS check lives in Appendix A, where the ruling puts it, and Appendix A is already run after every step.

## Appendix A — Validation checklist

Run after every build step. Every item must pass.

```
[ ] 1. GATE: Did this step end with one exposure, carrying its band's feedback
       request, in front of the named person? If no → the step is not done.
[ ] 2. SIGNAL MATCHES BAND: Is the signal sought the one defined for the current
       band in 1.0? If no → realign.
[ ] 3. ONE SCREEN: Does first contact still fit one screen? If no → move depth
       into docs/.
[ ] 4. CONCESSION: Does new public copy concede what a competitor does better
       before distinguishing? If no → rewrite the opening.
[ ] 5. SOURCED: Does every factual claim added carry a source and a verification
       date? If no → source it or cut it.
[ ] 6. RENAME-CHEAP: Does anything added depend on the name in a way
       find-and-replace cannot fix? If yes → refactor to the constant.
[ ] 7. NO API CALLS: Does anything added require a key, server, quota, or
       account? If yes → revert.
[ ] 8. MATCHES ANCHOR: Does the output contradict any section of this document?
       If yes → revert.
[ ] 9. NO CREEP: Does the output add anything not specified here? If yes → remove
       it, or add a section to this anchor first.
[ ] 10. LEDGER: Was the step, its outcome, and any override appended to
        state/use-ledger.md? If no → append before committing.
[ ] 11. NO DEAD ENDS: Does any actor's journey now end without them learning
        the outcome of their action (Section 8.4)? If yes → that is a missing
        feature, not a bug. Halt and report.
```

## Appendix B — Glossary

| Term | Definition |
|---|---|
| Anchor sentence | The Section 1.0 statement binding the build to a named person, a result in their world, and an externally generated signal |
| Architect's trap | Producing architecture as a substitute for shipping product; the diagnosed failure this methodology corrects |
| Band | A release stage (Prototype, MVP, v1) whose boundary is a proof gate, not a date |
| Drift | Decisions failing to survive across sessions, tools, operators, or projects — as distinct from within-session goal drift |
| Exposure | A single instance of the product, or a piece of it, reaching the named person |
| Proof gate | A band boundary, crossed only when the band's defined signal has been observed |
| Quarantined metric | A real but non-decisive number (stars, traffic, forks) explicitly barred from triggering a band transition |
| Use ledger | The append-only record of what was tried, what failed, and what was skipped with which reason |
| Variant | The same methodology with an anchor shaped for a specific domain |

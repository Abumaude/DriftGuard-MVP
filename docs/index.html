Project governance in three markdown files.

No CLI, no account, no server, no database, and not a single API call. Your AI forgets what you decided last Tuesday — worse, it doesn't know that it forgot, so it invents a reason, you build on the invention, and three weeks later you're deleting the repo. DriftGuard is the boring fix: write the decisions down in a file the AI reads at the start of every session and is never allowed to rewrite.

the gate names me

This project governs itself with its own methodology, which means publishing the parts that do not flatter it. The anchor requires a named person before any build action, and that person is the author. It fails one of its own three tests — the signal is meant to come from someone other than the operator — and the failure is recorded in the anchor rather than waived. quick start

Start with two sections of one file

Copy the two templates

Take ANCHOR_TEMPLATE.md and BUILD_INSTRUCTIONS_TEMPLATE.md from templates/ into your project's repo, as ANCHOR.md and BUILD_INSTRUCTIONS.md.

Fill sections 1.0 and 1.1 — then stop

A named person you could message this afternoon, a change in their world, and a signal somebody other than you generates. Then stop. Filling in the whole document before building anything is the exact failure this prevents.

Point any AI at it

Paste: Read BUILD_INSTRUCTIONS.md and ANCHOR.md Section 1 from the repo. Then run Step 0. That is the whole install — no package, no CLI, no account.

how it works

Three files, all plain text, no magic

Nothing to install. If you can put a file in a folder, you can run this. Every term on this page is in the glossary, one line each, in ordinary words.

The constitution ANCHOR.md

What you are building, who for, and the rules that must never be broken. The AI reads it and never rewrites it. When its output contradicts the anchor, the output is wrong — not the anchor. It grows by adding sections; you never edit or delete one. That is the rule people find strangest and the one doing most of the work.

The sequence BUILD_INSTRUCTIONS.md

Which part of the anchor to load at each step, so you never dump the whole thing in and get it skimmed. Each step names its model, its inputs, how to check the work, and what to save. It ends with a copy-paste prompt for the next session — which sounds trivial and is the reason people keep using it.

The memory git

State lives in the repo, not in a chat window and not on one laptop. It survives a wiped machine, a switched tool, a provider outage, and somebody else picking the work up cold.

Without an anchor

Youwhy does the auth flow block requests from the same IP twice in a row?

AIThat’s a standard rate-limiting pattern to prevent brute-force attacks. It’s good practice to keep it.

Confident, plausible, entirely invented. The real reason was a payment sandbox limit you hit in week one and worked around. Four days later you remove the “rate limiting”, payments break, the rollback undoes something else, and you’re managing the codebase instead of building it.

With an anchor

Youwhy does the auth flow block requests from the same IP twice in a row?

AIANCHOR.md Section 4 records this: the payment sandbox rejects duplicate calls within 2s from one IP (logged 2026-06-14, see state/use-ledger.md). The block is a workaround for that, not rate limiting. Removing it will break checkout in the sandbox.

Same model, same question. The difference is that the answer had somewhere to come from.

before you adopt

What this does not do

It is free and asks for nothing, so there is no purchase to protect you from — but adopting a working method costs time, and switching away later costs more. The short version is here; the full disclosure lists the limitations a fair competitor would attack.

Do not adopt this if

You are building one codebase with one agent. Use Spec Kit — more mature, far larger community, better at that job. It is also the most common case, so this is not a courtesy.

You want better output within a session. This governs what the AI may do; it does nothing to improve what it generates.

You want something to install, or a dashboard to log into. There is neither, and there will not be.

You will not write things down. The method is writing things down. No automation removes that.

Known limitations

Unproven. Nobody outside the author has completed a project with it. Not one person. The evidence supports the problem being real; it supports nothing about this being the right answer.

Nothing is enforced. An AI can ignore the anchor, and will, unless prompted to read it. No runtime, no hook, no interception.

Not an attested record. It is a git history — anyone with write access can rewrite it. Not fit for compliance or audit evidence.

The templates are written for developers, which contradicts the stated first market. Named openly as the known weak point, and not yet fixed.

Conflict of interest. Every claim and verification date on this site comes from the author working with an AI assistant in one session. That is internal review — not an audit, not independent, not attested by anyone outside this project. Each claim is logged with its evidence tier and limits in the evidence ledger, including three currently marked quarantined, meaning unsourced and not fit to state as fact.

positioning

One word, five scopes

Everyone is now using drift language, and they all mean something different by it. Each of the first four is bounded by a boundary this project is defined by crossing. If you are building one codebase with one agent, use Spec Kit — it is better at that, and it composes with this.

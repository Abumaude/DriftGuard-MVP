## 0. How to use this document

This is the **immutable design anchor** for your project. AI agents read from it but never modify it. If an agent's output contradicts this document, the output is wrong.

**Structure rules.** Section 1 is loaded into every AI session as mandatory context. All other sections are loaded selectively — only when `BUILD_INSTRUCTIONS.md` specifies them. Every section must be self-contained: an agent reading Section 5 should understand it without needing Section 7. The validation checklist in Appendix A runs after every build step.

**Growth rule.** The anchor grows by **section addition**. Sections are not edited in place and not versioned in place. If a decision changes, append a new section recording the change and why. The old section stays as the record of what was believed at the time.

> **New here?** Fill Section 1.0 and 1.1 first, then stop and go do Step 0 of `BUILD_INSTRUCTIONS.md`. Do not fill in the whole document before building anything — that is the failure this methodology exists to prevent. Sections 2 onward get filled as the build reaches them.

## 1. Architecture anchors (immutable context)

_Loaded into every AI session. These do not change._

### 1.0 Ship-or-drift front gate

_The first thing read in every session and the precondition for all build action. It exists to keep production pointed at a real outcome instead of accumulating output no one has seen. Fill the three slots with something real. If you cannot, you are producing output for its own sake — which is allowed, as long as you admit it and label the project an experiment._

**Anchor sentence:**

> This exists so that **[a named person I can message today]** can **[a change in THEIR world]**, and I'll know it worked when **[a signal someone other than me generates]**.

_Slot tests, each of which must pass before any build begins:_

**Named person.** A human with a name you can message this afternoon — not "users," not a demographic. A named person can reject you; a demographic cannot. That discomfort is the point.

**Result.** A change in *their* world, not a feature of your tool. "AI-powered X" is a feature; "goes from two replies to five interview calls in a fortnight" is a result.

**Signal.** Generated by someone other than you. "I shipped it" is not a signal. "They paid," "they used it twice," "they replied" are.

#### Ship cadence

_Set this once, before building. It governs how often you must ship **within** a band. It does not govern the band proof gates, which are fixed._

- **Every step** — each build step ends with an exposure. Strictest; the default.
- **Once per band** — build several steps, but at least one exposure must reach the named person before the band's proof gate.
- **Override-logged** — ship when you choose, but every skipped ship is recorded with a one-line reason.

> Chosen cadence: **[every step / once per band / override-logged]**

Overrides are never blocked — they are logged. A skipped ship costs one line: `drift: [date] — shipped nothing because ___`. The accumulating log, not a locked door, is what keeps the rule honest: a run of overrides is itself the signal that you are drifting.

#### Signal and feedback ladder

_Complete this table at product-definition time. The gate is fixed; what the feedback request **is** depends on the product, so it is defined here, once, per stage._

_Each feedback request must elicit a **behaviour or a concrete answer**, not a vanity "do you like it?" The signal that counts escalates as the product matures._

| Release band | Named-person reach | Feedback request | Signal that counts |
|---|---|---|---|
| **Prototype** | One named person | [e.g. "send a recording and ask: could you do X with this?"] | They reacted, or gave a reason why not |
| **MVP** | A handful in the role | [e.g. "watch them complete the core action, ask the one blocker question"] | They used it twice, or completed the core action unaided |
| **v1** | Public or paid audience | [e.g. "checkout plus one post-purchase question"] | They paid |

_Optional but recommended: list your **quarantined metrics** here — numbers you will watch but that are barred from clearing a proof gate. Stars, followers, traffic, and signups are the usual suspects._

## Appendix A — Validation checklist

_Run after every build step. Every item must pass._

```
[ ] 1. GATE: Did this step end with one exposure, carrying its band's feedback
       request, in front of the named person? If no → the step is not done.
[ ] 2. SIGNAL MATCHES BAND: Is the signal sought the one defined for the
       current band in 1.0? If no → realign.
[ ] 3. [PRINCIPLE 2]: [Test question]? If fail → [action].
[ ] 4. [PRINCIPLE 3]: [Test question]? If fail → [action].
[ ] 5. MATCHES ANCHOR: Does the output contradict any section of this
       document? If yes → revert.
[ ] 6. NO CREEP: Does the output add anything not specified here? If yes →
       remove it, or add a section to this anchor first.
[ ] 7. LEDGER: Was the step, its outcome, and any override appended to the use
       ledger? If no → append before committing.
[ ] 8. NO DEAD ENDS: Does any actor's journey now end without them learning the
       outcome of their action (Section 3.1)? If yes → that is a missing
       feature, not a bug. Halt and report.
```

| Proof gate | A band boundary, crossed only when the band's defined signal has been observed |
| Quarantined metric | A real but non-decisive number, explicitly barred from clearing a proof gate |
| Use ledger | The append-only record of what was tried, what failed, and what was skipped with which reason |
